# Receipts

**A catfish detector.** Give it a public Instagram handle and it scores what that
person *claims* to be into against what their posts actually prove — then tells
you whether the account looks mass-produced.

Built at the Austin Elastic HackNight with Apify.

```
@somehandle — 3/10  (confidence: high)
Bio reads like an outdoors influencer; the posts are almost entirely indoors.
Foodie is the one claim that actually holds up.

interest     claims       evidence     receipt
outdoorsy    ████████··  █·········   1 of 12 captions mentions a trail
travel       █████████·  ██········   every geotag is the same city
fitness      ████████··  ██········   one gym photo, 2022
foodie       ███████···  ██████····   6 of 12 captions are restaurants

Similar accounts in index: 6
  @other_one   similarity 0.91 [previously flagged]

⚠ ring_score 0.89 — this bio reads as a reworded copy of accounts already indexed.

A low score means unverified or inconsistent. It does not mean proven fake.
```

---

## Why each tool is here

**Apify — because there is no API for this.** Instagram's Graph API only exposes
accounts you own; there is no endpoint for reading someone else's public
profile. Scraping is the only path to this data. Apify absorbs the anti-bot
handling, pagination, and proxy rotation, and its `run-sync-get-dataset-items`
endpoint runs the actor and returns rows in a single HTTP call — so the whole
ingest is one request, not a polling loop.

**Elasticsearch — because a single profile cannot be fake.** One person
exaggerating in a bio is just a person exaggerating. *Fake* is a pattern across
accounts: the same bio reworded, posted a dozen times, by accounts created the
same month. Seeing that requires memory of everything scored so far, searched by
**meaning** rather than by exact words — because the whole point is that the
copies are reworded. That's vector search, and neither BM25 nor Postgres can do
it.

Elasticsearch is this project's **memory and context layer**, not its database.
All four capabilities are load-bearing:

| Capability | Where | What it does here |
|---|---|---|
| **Keyword (BM25)** | `Memory.keyword_search` | Exact tokens vectors blur — a shared external link, a handle pattern, a specific emoji run |
| **Semantic (`semantic_text`)** | `Memory.semantic_search` | Finds the same bio in different words. Embeddings are generated by Elastic, so there's no embedding service to run |
| **Hybrid (RRF)** | `Memory.hybrid_search` | Fuses both in one query. Rings reword the bio but reuse the link — semantic alone misses the link, keyword alone misses the rewrite |
| **Aggregations → Kibana** | `Memory.ring_fingerprint`, `creation_histogram`, `gap_by_interest` | `significant_text` *discovers* what fake bios have in common. The word list is never written by hand |

`recall()` runs **before** the model is called, and its results go into the
prompt. `remember()` runs after. That is the memory loop: the tool gets better at
spotting fakes every time it's used.

**Claude — because the scoring needs judgment with a citation.** It has to say
*why*, quote a real caption, and refuse to invent a receipt when the evidence is
thin. Structured outputs (`output_config.format`) constrain the response to a
Pydantic model, so the score lands in a typed field instead of being parsed out
of prose.

## Architecture

```
             ┌──────────────────────── memory loop ────────────────────────┐
             │                                                             │
handle ──► Apify ──► recall (hybrid: semantic + exact) ──► Claude ──► remember
        (scrape)         │                                    │           │
                         └──── prior profiles as context ─────┘           │
                                                                          ▼
                                              Kibana: significant_text, gap chart
```

Recall deliberately precedes the write. If a profile were indexed first, a
re-score would retrieve *itself* as a near-perfect match and drive its own ring
score to 1.0. There's a test pinning that ordering.

## Layout

```
src/receipts/
  config.py         env loading + explicit validation per subsystem
  models.py         Pydantic schemas; Verdict is the model's output contract
  apify_source.py   scrape one public profile, normalize it
  memory.py         Elasticsearch as memory: BM25 / semantic / hybrid / aggs
  judge.py          LLM scoring via structured outputs
  signals.py        objective risk checks, so the score can explain itself
  seed.py           labelled synthetic ring cohort for the aggregations
  pipeline.py       scrape -> recall -> judge -> remember
  cli.py            init | score | similar | fingerprint | histogram | gaps | seed-ring
infra/mappings.json the index mapping, shared by code and Dev Tools
docs/DEMO.md        5-minute demo script
docs/GLOSSARY.md    plain-English explanations of every term used
GUIDE.md            full setup, commands, troubleshooting, known limitations
tests/              48 tests, no network or credentials required
```

## Setup

See **[GUIDE.md](GUIDE.md)** for the full walkthrough. Short version:

```bash
make setup                  # venv + deps
cp .env.example .env        # then fill it in
make test                   # 48 tests, no credentials needed
make init                   # create the index
make score HANDLE=someone
```

Add `--dry-run` to `score` to exercise the whole pipeline with an offline stub
verdict — the scrape, recall, and indexing all still run, only the judgment is
stubbed. Useful before a model key is configured.

## What the output shows

Two things, explicitly: **what the bio claims vs. what the posts prove**, and
**why the score is what it is**.

```
  @example_suspect
  LIKELY MASS-PRODUCED — this bio matches a template shared with other accounts
  authenticity 2/10   ·   template match 0.89   ·   confidence high

  INTERESTS — what the bio says vs what the posts prove
  interest    SAYS         POSTS SHOW    GAP  evidence
  travel      █████████·  ··········    +9  no location or travel content in any post  <
  fitness     ████████··  █·········    +7  'back at it' is the only gym reference     <

  WHY THIS SCORE
    ✗ template bio         bio similarity to template cohort: 0.89 — above threshold
    ✗ new account          Instagram flags this account as recently created
    ✗ thin history         7 posts total — little to verify a bio against
    ✗ lopsided following   follows 4,400 but only 1,203 follow back
    · no captions          2 captions available as evidence
```

The `WHY THIS SCORE` block is arithmetic, not model prose — every line is a check
against scraped data, so it's reproducible and can't be hallucinated. Checks that
*didn't* fire are shown too, so you can see what was ruled out.

## Testing approach

The tests run with no Elasticsearch, no Apify token, and no Anthropic key:

- **Profile parsing** is tested against a **real** `apify/instagram-scraper`
  response (`tests/fixtures/raw_profile.json`, a public institutional account).
  Real output rather than a hand-written dict, so the actor's genuine field names
  are locked in.
- **Query construction** is tested with a recording client that captures request
  bodies. Each of the four Elasticsearch capabilities has assertions on the query
  it produces — including that `significant_text` targets the analyzed field and
  not the `semantic_text` one, which is a silent-failure trap.
- **Pipeline ordering** has an explicit test that recall precedes write.

## Notes and gotchas found the hard way

- **Never pass `temperature`.** Sampling parameters were removed on Claude
  Opus 5 and return a 400. Determinism comes from the prompt.
- **`max_tokens` covers thinking too.** Thinking is on by default on Opus 5, and
  `max_tokens` caps thinking *plus* response text — size it above the JSON.
- **`bio` and `bio_raw` hold the same text on purpose.** `semantic_text` powers
  kNN; analyzed `text` powers BM25 *and* `significant_text`. Dropping either
  silently removes a capability.
- **Apify's sync endpoint hard-caps at 300s** and returns 408 past it. Keep
  `resultsLimit` small.
- **`latestPosts` arrives with the profile** — one actor call yields bio and
  captions together. No second request.

## Scope

Public accounts only; a private handle raises rather than being partially
scraped. The tool checks self-published claims for internal consistency. It does
not profile the people a subject follows, and it does not infer anyone's gender.
A low score means *unverified*, never *proven fake* — the CLI prints that with
every result.
